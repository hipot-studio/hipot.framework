# SQL-профилирование отдельной страницы

Самостоятельный скрипт `src/lib/sql_profile.php`, без Composer и внешних библиотек.
Записывает SQL одного HTTP-запроса в штатный модуль «Монитор производительности» (`perfmon`).
Глобально включать монитор не требуется. Модуль `perfmon` должен быть установлен.

## Подключение на сайте

Добавьте в `/bitrix/php_interface/after_connect_d7.php` следующий код,
сохранив существующее содержимое файла. Пример предполагает установленный модуль в `/local/modules/hipot.framework`;
скорректируйте путь под свой сайт:

```php
// Задайте SQL_PROFILE_SECRET в окружении PHP-FPM/Apache, не храните секрет в репозитории.
define('BITRIX_SQL_PROFILE_VALUE', getenv('SQL_PROFILE_SECRET') ?: '');

require_once $_SERVER['DOCUMENT_ROOT'] . '/local/modules/hipot.framework/lib/sql_profile.php';
```

При ручном копировании достаточно перенести `src/lib/sql_profile.php` на сайт и изменить путь подключения.
Не подключайте этот скрипт из обычного `init.php`: раннее подключение позволяет захватить больше запросов.
Запросы до запуска профайлера в отчёт не попадают.

## Как сделать замер

1. Откройте нужную страницу с параметром `?BITRIX_SQL_PROFILE=ваш-секрет`.
   Если в URL уже есть параметры, используйте `&BITRIX_SQL_PROFILE=ваш-секрет`.
2. После завершения запроса откройте `/bitrix/admin/perfmon_hit_list.php?lang=ru`.
3. Найдите хит по адресу и времени и перейдите к его SQL-запросам.

Совет: можно вывести в списке хитов колонку `ID` и отсортировать по убыванию — последние замеры будут сверху.

Без секрета, с неверным значением или массивом вместо строки профайлер не запускается.
Проверяется только GET-параметр: cookie не включает сбор для всех последующих страниц.
AJAX-запросы — отдельные хиты; для их замера параметр нужно передать в адрес самого AJAX-запроса.
Если страницу целиком отдал внешний или композитный кеш без выполнения PHP, отчёт не появится.

Секрет в URL может сохраниться в журналах веб-сервера, истории браузера и `REQUEST_URI` отчёта.
Используйте временный секрет и удаляйте его из окружения после диагностики.

## Особенности реализации

Скрипт проверяет GET через `hash_equals`, запускает SQL tracker основного соединения
и при завершении PHP сохраняет хит в `b_perf_hit`, а SQL — через `CPerfomanceKeeper::saveQueries()`.
Перед сохранением трекер останавливается: SQL самого отчёта не попадает в замер.
Запросы других соединений не собираются. SQL не распределяется по отдельным записям компонентов;
суммарная статистика компонентов берётся из `arIncludeDebug`, если она доступна.
Запросы последующих shutdown-обработчиков в отчёт не попадут.

Если SQL tracker уже существует (даже остановленный), скрипт пропускает замер и пишет причину в PHP error log.
Повторное подключение через `require_once` не создаёт второй отчёт.
Не совмещайте замер с глобальным сбором perfmon или другим SQL-профайлером:
если другой код заменит или сбросит трекер после запуска, отчёт может отсутствовать или оказаться неполным.
При отсутствии установленного `perfmon` скрипт ничего не делает.
Ошибки сохранения перехватываются и отмечаются в PHP error log без SQL и секрета.
Сбор SQL добавляет накладные расходы; сравнивайте варианты при одинаковых настройках кеша и профилирования.
Накладные расходы не измерялись.
